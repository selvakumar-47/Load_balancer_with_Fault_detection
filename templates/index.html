Load-Balancing Scheduling Algorithms Deterministic Routing

Select the scheduling algorithm used by the reverse proxy to distribute client requests across healthy backend servers. Requests are only routed to servers that are enabled, healthy, and whose circuit breaker is in the CLOSED state.

1. Round Robin Modulo Cyclical

Equally alternates incoming requests across available servers in sequential order using an atomic counter:

target_index = (atomic_counter++) % num_eligible_servers
  • Best suited for homogenous servers with identical compute capacity.
  • Thread-safe with atomic index wrapping.
2. Weighted Round Robin Smooth Nginx Algorithm

Distributes requests proportionally to server compute weights (e.g., Alpha=3, Beta=2, Gamma=1) using a smooth deficit round-robin algorithm:

current_weight[i] += weight[i]; best = max(current); best -= total_weight;
  • Prevents burst clustering by smoothly interleaving requests.
  • Server with weight 3 receives 50% of traffic in a 3-2-1 cluster.
3. Least Connections Dynamic Active Tracking

Inspects real-time concurrent active requests currently in flight on each server and directs new traffic to the server with the lowest active load:

eligible = argmin(active_connections[s]); tie_break = lowest_latency || round_robin
  • Ideal for heterogeneous workloads with varying request execution times.
  • Connections are incremented atomically on dispatch and decremented in a guaranteed finally block upon response.

Academic Mini-Project Documentation & Architecture CSE Mini-Project

1. Project Abstract & Objective

Modern distributed web architectures rely on load balancers to achieve high availability, fault tolerance, and horizontal scalability. Standard load balancers often lack intelligent, localized circuit breakers, continuing to forward traffic to failing instances until coarse health checks trigger. This project implements a full-stack, enterprise-grade Load Balancer with Fault Detection and Automatic Recovery.

It features an RFC-compliant HTTP reverse proxy, three scheduling algorithms (Round Robin, Smooth Weighted Round Robin, and Least Connections), an autonomous per-backend Circuit Breaker state machine (CLOSED ↔ OPEN ↔ HALF-OPEN), a background health prober, and a Fault Detection and Recovery Intelligence Dashboard.

2. Architecture & Request Pipeline

[Client / Browser] ↓ (HTTP Request: /proxy/*) [Flask Reverse Proxy (app.py :5000)] ↓ (Query Eligible Backends) [Server Registry (SQLite + Memory Cache)] ↓ (Filters: Enabled=1, Status!=UNHEALTHY, Circuit=CLOSED) [Scheduling Algorithm (Round Robin / Weighted / Least Connections)] ↓ (Selected Eligible Backend) [Forward HTTP Request + Strip Hop-by-Hop Headers] ↓ (Track Active Connection Count) [Backend Server Alpha:8001 / Beta:8002 / Gamma:8003] ↓ (Return Response) [Metrics Engine + Circuit Breaker Result Logger]

3. Circuit Breaker Lifecycle & State Transitions

  • CLOSED: The backend is operating normally. In-flight and new requests are dispatched freely. If consecutive failures reach the configured failure threshold (default: 3), the circuit transitions to OPEN.
  • OPEN: The backend is isolated from all user proxy traffic. An isolation timestamp is saved. While in OPEN state, user traffic is routed exclusively to remaining healthy backends. When the recovery delay (default: 5.0s) elapses, the circuit automatically transitions to HALF-OPEN.
  • HALF-OPEN: Normal client traffic remains excluded. Dedicated background health probes test the backend. If a probe fails, the circuit reopens to OPEN. If consecutive successful probes reach the recovery threshold (default: 2), the circuit transitions back to CLOSED, fully restoring traffic routing.

4. Mathematical Definitions of Metrics

  • Fault Detection Latency ($T_{\text{detect}}$): The exact elapsed duration from the controlled fault-injection timestamp ($t_{\text{fault}}$) until the health checker detects the failure threshold and triggers the circuit to OPEN ($t_{\text{open}}$):
    $T_{\text{detect}} = t_{\text{open}} - t_{\text{fault}}$
  • Recovery Duration ($T_{\text{recover}}$): The elapsed duration from when a backend is healed ($t_{\text{heal}}$) until successful probes restore the circuit to CLOSED ($t_{\text{closed}}$):
    $T_{\text{recover}} = t_{\text{closed}} - t_{\text{heal}}$
  • Failover Continuity: The percentage of requests that successfully returned status < 500 through surviving healthy backends while a peer backend experienced failure.

5. Known Limitations & Single-Point-of-Failure (SPOF) Analysis

As an academic mini-project running locally, the load balancer process itself runs on a single host (Port 5000). In a hyperscale production deployment, high availability for the load balancer tier itself is achieved using redundant nodes coordinated via Virtual Router Redundancy Protocol (VRRP), Keepalived, or BGP Anycast routing.
